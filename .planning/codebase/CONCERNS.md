## Security Concerns

### Self-update binary integrity (intentional limitation, document it)

- `packages/cli/internal/selfupdate/selfupdate.go:304-308` — direct binary self-update is intentionally disabled. The function only emits a "download the latest release from …" instruction and never replaces the executable. The Go-generated code at `selfupdate.go:450-484` (`replaceExecutable`) and the archive extractors at `selfupdate.go:359-448` exist and would be reused, but they are reached only via the `InstallMethodNPM` (`npm i -g`) and `InstallMethodHomebrew` (`brew upgrade`) paths. Users who run a `go install`-ed or otherwise "direct" binary cannot self-update by design, because the release asset's SHA-256 is not anchored to a trust root that the CLI can verify offline (no cosign / sigstore check). This is a security choice, not an oversight, but it is the kind of choice that future contributors will "fix" by re-enabling the function. Treat the `fmt.Errorf` as load-bearing.
- `packages/cli/internal/selfupdate/selfupdate.go:321-350` — `downloadToFile` and the tar/zip extractors at `selfupdate.go:359-448` open the archive, find the entry whose `path.Base(header.Name)` matches the platform binary, and `os.Create(filepath.Join(destination, binaryName))` (`selfupdate.go:386`, `selfupdate.go:426`). Because the destination directory is a fixed `os.TempDir` (the call site in `Run` does not currently pass a path because `updateDirectBinary` short-circuits), there is no path-traversal vector in production today, but the extractors do not validate that the resolved path stays inside `destination`. A refactor that re-enables `updateDirectBinary` and accepts a user-supplied `destination` would re-introduce CVE-2018-7187-style traversal. Lock the extractors to that pattern even after the trust-root work lands.

### Tarball / zip extraction hardening

- `packages/cli/internal/selfupdate/selfupdate.go:382` and `selfupdate.go:418` use `path.Base(header.Name) != binaryName` to locate the binary. `path.Base` on Windows accepts both `/` and `\` separators per the Go stdlib contract, so a crafted tar with backslash separators would not help, but on POSIX this comparison is fine. The risk is `header.Name` containing an absolute path; `os.Create(filepath.Join(destination, binaryName))` then makes `destination` the trust boundary. Reinforce by `filepath.IsLocal(header.Name)` checking before `path.Base` (would need a small Go 1.20+ `path/filepath` call).

### Network trust

- `packages/cli/internal/selfupdate/selfupdate.go:245-260` — `fetchLatestRelease` issues a plain `http.NewRequestWithContext` to `https://api.github.com/repos/sergiocarracedo/skill-organizer/releases/latest` (`selfupdate.go:29`). No `User-Agent` is added that the request layer enforces, and the URL is hard-coded. If the host becomes a typosquat, there is no pin. The 10s timeout (`selfupdate.go:252`) is the only mitigation.
- `packages/cli/internal/remote/skillscli.go:97-105` — `DetectSkillsCLI` uses `exec.LookPath("skills")` and `exec.LookPath("npx")`. If the user has a `skills` binary on `$PATH` that is not the genuine `skills.sh` CLI, the sandbox in `skillscli.go:148-168` will execute it with `CombinedOutput()` and read its `stdout`. The `sandboxEnv` (`skillscli.go:133-146`) sets `HOME`, `FORCE_COLOR=0`, `NO_COLOR=1`, `CI=1`, and disables npm update notifiers, but it does not pin `PATH` or `NPM_CONFIG_REGISTRY`. A malicious or shadowed `skills` binary would still be able to write into `sandbox.homeDir` because the project dir is created with `0o755` (`skillscli.go:160-165`). This is acceptable for a developer tool but worth noting if anyone tightens the trust model.
- `packages/cli/cmd/skill_overlap.go:55` — `launchPlanSession` runs `exec.Command(tool.Binary, tool.Tool.PlanArgs(prompt)...)` with the user's stdin/stdout/stderr attached. The tool binary comes from `agenttools.DetectInstalled` (`agenttools.go:150-157`), which only checks `exec.LookPath`. There is no signature check. The "acknowledged external tool costs" prompt (`skill_overlap.go:133-142`) is the only friction. This is a known design decision (the user has to install the tool themselves), but the prompt does not warn that the CLI is forwarding the prompt to an arbitrary local binary.
- `packages/web/src/views/home/hero/HeroWaves.astro:55-56` — the hero background loads two remote scripts at runtime: `https://cdnjs.cloudflare.com/ajax/libs/three.js/r121/three.min.js` and `https://cdn.jsdelivr.net/npm/vanta@latest/dist/vanta.waves.min.js`. Both URLs are pinned to immutable paths / package versions, but `@latest` is **not** pinned. A future malicious vanta release would execute immediately. There is no SRI hash. The `prefersReducedMotion` guard at `HeroWaves.astro:51-53` is unrelated. Either pin to a specific version or add an `integrity` attribute.
- `packages/web/src/components/GitHubStarButton.astro:82-103` — `fetch(apiUrl, { headers: { Accept: 'application/vnd.github+json' } })` with a silent `.catch(() => {})`. No SRI, no rate-limit backoff, no auth (so it is unauthenticated and subject to the public-API rate limit). The fallback `1` star at `GitHubStarButton.astro:17` is a static string that ships to all visitors. A failed fetch leaves a literal "1" in the badge.

### Input validation

- `packages/cli/cmd/skill_add.go:122` constructs `SourceURL: "https://github.com/" + strings.Trim(source, "/")` from the unvalidated `source` argument. If the user passes a non-short source like `https://gitlab.com/owner/repo`, this produces `https://github.com/https://gitlab.com/owner/repo` which then gets written into `metadata.skill-organizer.source`. `remote/skillscli.go:510-527` does better URL handling for `sourceToGitHubURL`, but `cmd/skill_add.go:122` is a code path that bypasses it. Worth a unit test.
- `packages/cli/cmd/skill_delete.go:141-150` — `filepath.Match(pattern, item.RelativePath)` accepts `*`, `?`, `[`. A pattern like `*` (no slash) is a valid `filepath.Match` and matches every top-level skill; `**` is not a real pattern (Go's `filepath.Match` is single-segment), so the README's "Quote wildcard patterns" guidance at `README.md:248-250` is only partially true. Users with a habit of writing `**` will silently get no matches.
- `packages/cli/internal/config/path.go:29-50` — `expandAliases` runs `os.Expand` on the input. `$VAR` references in `source:` or `target:` in `.skill-organizer.yml` are expanded from the calling process environment. This is documented in the README and is intentional, but `os.Getenv` is called without any sanitization, so a config with `source: "$HOME"` will resolve to the caller's home, which is the right behavior, while `source: "$(rm -rf /)"` would not be invoked because Go's `os.Expand` does not interpret shell — only `$NAME` and `${NAME}`. So no shell injection, but the read-me does not mention that `~` is also expanded.
- `packages/cli/internal/skills/frontmatter.go:62-88` — `sanitizeFrontmatter` is invoked from `ParseDocument` (`frontmatter.go:41-53`) **only when the first `yaml.Unmarshal` fails**. The sanitizer quotes only unquoted scalar values that contain `": "` and skips lines starting with `#` (correct, comments), but the function operates on raw lines without honoring YAML block scalars (`|` / `>`). A perfectly valid multi-line `description: |` block will not be re-quoted; if it ever triggered the fallback, the rewrite would corrupt the file. The fallback path is unreachable in practice for well-formed input, so this is mostly "future-proofing" rather than an active bug.

### Path traversal

- `packages/cli/internal/skills/scanner.go:130-132` and `scanner.go:165-167` explicitly block `..`-escape via `strings.HasPrefix(filepath.ToSlash(relPath), "../")`. The `sync` engine at `internal/sync/sync.go:117-153` then creates symlinks with relative paths. As long as a skill's directory is under the source root, the symlink is safe; if a future command line ever let users pass an arbitrary directory, traversal would be possible. The `Sync Run` invariant depends on `ScanSource` first — it does not re-validate.
- `packages/cli/cmd/skill_add.go:312-326` (`writeImportedBundle`) uses `filepath.Join(targetDir, filepath.FromSlash(file.Path))` and `os.MkdirAll(filepath.Dir(path), 0o755)`. The `bundle.Files` come from the embedded fake `skills` CLI in `testdata/fake-skills-cli.go:317-345` or from the real one. The fake serializes `filepath.ToSlash(filepath.Rel(root, path))` (`skillscli.go:330-334`); on Windows this can produce paths with backslashes, which `filepath.FromSlash` then converts back. `filepath.Clean` is not called on the joined path, so a `..` in a `RepoSkillPath` would escape. The fake does not produce `..`, but the public `skills.sh` CLI might, and the real path is not sanitized before being written.
- `packages/cli/cmd/skill_overlap.go:481-497` (`writeApplyPlanPrompt`) joins the CWD with a fixed filename template. The prompt content is written verbatim. No user input flows into the path, so no traversal; calling out only because plans/ is a new directory that the CLI starts creating.

### Sandbox / process handling

- `packages/cli/internal/overlap/process_unix.go:10-23` and `process_windows.go:7-14` — interrupt handling on Unix uses `syscall.Setpgid: true` to put the child into its own process group, then signals `-pgid` with `SIGINT` on cancellation. On Windows there is no `Setpgid`, so the only interrupt is `cmd.Process.Kill()` (effectively `TerminateProcess`), which leaves any subprocesses the agent tool spawned orphaned. The `select { case <-ctx.Done(): … }` at `overlap.go:338-343` is reachable on both platforms, but the Windows cleanup is coarser.
- `packages/cli/internal/remote/skillscli.go:114-131` (`RunIn`) runs the `skills` / `npx skills` command with the parent process stdin/stdout. `npx` will prompt the user interactively if it needs to; the CLI's `sandboxEnv` at `skillscli.go:133-146` sets `CI=1` to suppress this, but a non-`npx` `skills` binary would still see the parent's stdin and could consume it.

## Performance Bottlenecks

- `packages/cli/cmd/skill_check_updates.go` is 756 lines (largest in the repo). `collectUpdateCandidates` does an `npx skills add` for **every imported skill with a source** in a per-skill sandbox, then a second `sandbox.ListRepoSkills` via `npx` (`internal/remote/skillscli.go:178-206` / `:368-395`). For a repo with N imported skills, this is N sandbox create + N `npx skills` round-trips in series. The watcher in `internal/watch/watch.go:146-195` (`collectSkillUpdates`) does the same on its 24h ticker. There is no parallelism, no caching of the upstream bundle list, and no fast path. This is the dominant cost of `skill check-updates` and the watch service's update check.
- `packages/cli/internal/skills/frontmatter.go:204-220` (`Marshal`) marshals via `yaml.Marshal(&d.frontmatter)` (the whole document node), not via a streaming writer, then re-wraps with `---\n…\n---\n`. The `clone()` helper at `frontmatter.go:301-311` does a full `Marshal → ParseDocument → Marshal` cycle, which is the worst-case for the YAML library. Every `WithoutManagedMetadata()` call (`frontmatter.go:108-120`) and every `RewriteManagedFieldsWithMetadata` (`frontmatter.go:317-333`) pays this cost. For a repo with hundreds of skills the rewrite becomes noticeable on every `sync` run.
- `packages/cli/cmd/skill_overlap.go:541` (largest cmd file) — the overlap command, including the agent prompt builder at `internal/overlap/overlap.go:90-` and the spinner status updates, spins while the agent tool processes a multi-KB prompt. There is no streaming output: `runCommand` (`overlap.go:287-357`) buffers both streams and only surfaces a single status line per stderr chunk. For a long-running agent (Codex, Claude Code) the user sees a frozen spinner.
- `packages/web/src/data/home.ts` is 845 lines (largest web file). All terminal scenarios are statically inlined. Page weight is acceptable because Vite tree-shakes, but every page request re-evaluates the module. Not a real bottleneck.
- `packages/web/src/views/home/hero/HeroTransformPanel/components/HeroTransformPanelContent.astro` is 748 lines, runs `setTimeout` chains at lines 566, 613, 637, 644, 664. The animation logic is heavy; the user agent `prefers-reduced-motion` is **not** honored here (contrast with `HeroWaves.astro:51-53` which does honor it).
- The npm postinstall at `packages/cli/packages/npm/scripts/postinstall.js:1-185` downloads, checksum-verifies, and extracts the platform binary on every `npm install -g`. There is no cache, and the SHA-256 check (`postinstall.js:155-170`) parses the checksums file with a simple `find` and `split` — see the "checksum parse" note under "Fragile Areas" below.
- The `setup-go@v6` cache (`ci.yml:30-32`) and `pnpm/action-setup@v4` cache (`ci.yml:41-49`) both work, but the `cli-e2e` workflow at `cli-e2e.yml:33-37` does not set `cache-dependency-path: packages/cli/go.sum` despite running `go test`. Go module downloads are uncached → e2e job pays the full `go mod download` cost on every run. Combined with the 90s `testTimeout` constant at `e2e_test.go:22`, slow network conditions can flake.
- `packages/cli/e2e_test.go` is 691 lines and exercises real `pty` interaction (`e2e_test.go:18` imports `github.com/creack/pty`). `creack/pty` is the standard choice but pty tests are inherently flaky on shared CI runners. The 90s timeout per test is generous but not infinite. Expect intermittent red on `TestSkillAddAndCheckUpdatesBinary` when the runner is under load.

## Fragile Areas

- `packages/cli/internal/sync/sync.go:117-153` (`reconcileTargetEntry`) is the core safety property of the CLI: it is the only place that mutates the target directory. Touching it without re-reading `sync_test.go` and `e2e_test.go` will silently regress the "unmanaged entries are never deleted" guarantee.
- `packages/cli/internal/skills/frontmatter.go` is the most-touched file for sync/import work. `Marshal` re-emits the entire YAML document including fields we did not author. Reformatting during rewrite is a real risk; `frontmatter_test.go` covers it but only for a handful of shapes.
- `packages/cli/internal/config/registry.go` and `config.go` — `WatchRegistry.Normalize` deduplicates and sorts watched paths. Anyone adding a path-rewriting helper here must keep the clean→sort invariant or the watcher's reload loop will re-add duplicate watches.
- `packages/cli/internal/remote/skillscli.go:97-131` — the public `npx skills` CLI is treated as a stable contract, but its output is parsed by regex (`listedSkillPattern` at `skillscli.go:94` and `findResultPattern` at `skillscli.go:95`). Any change to the upstream `skills` table layout (column count, ANSI escapes) will silently produce empty `ListRepoSkills` results. The `ansiPattern` strip at `skillscli.go:93` and `extractJSONArray` at `skillscli.go:500-508` are best-effort.
- `packages/cli/internal/overlap/overlap.go:90-200` — `BuildPrompt` is a hand-written Go string builder. A stray template edit (e.g. dropping a closing brace) breaks the JSON contract for every agent tool, with no schema validation downstream until the agent responds.
- `.github/workflows/auto-merge-release-please.yml:28-65` — the cross-repo / branch-name / base-branch validation is a defensive shell script. Each `gh pr view` call adds a network round-trip. The script's title-check regex at line 59 (`grep -Eq -- '-(alpha|beta)\.'`) is the only thing preventing a beta-tagged PR from being auto-merged into `main`. If a future title convention stops including the prerelease suffix in the PR title (release-please does emit the suffix in the title today), this guard silently fails open.
- `packages/cli/internal/service/service.go:223-234` — the user-systemd unit is hand-formatted with `Sprintf`. Whitespace changes here are tolerated by systemd but `RestartSec=2` and `Type=simple` are load-bearing. The test at `service_test.go:33-34` is hard-coded to the homebrew path `/home/linuxbrew/.linuxbrew/bin/skill-organizer`; if you change the format string without updating the test, CI will not catch a subtle regression.
- `packages/cli/packages/npm/scripts/postinstall.js:155-170` — `verifyChecksum` parses the GoReleaser `checksums.txt` with `entry.trim().endsWith(` ${archiveName}`)`. The format GoReleaser emits is `<sha256>  <filename>` (two spaces) on most systems. The parser falls back to single-space matching at line 159, so it tolerates both, but if GoReleaser ever changes to one space, both checks still pass; if it switches to a hash-only format, this breaks. Low risk, fragile by design.
- `packages/cli/cmd/skill_overlap.go:55` (the `launchPlanSession` exec) — see "Network trust" above. Any caller that wraps this in a test must mock `exec.Command`; the production code is non-injectable (the variable `launchPlanSession` at line 51 is a `var` and can be replaced in tests, but the cmd-side helper at line 55 is not).
- `packages/web/src/views/home/hero/HeroTransformPanel/components/HeroTransformPanelContent.astro:463,506` — the panel uses `innerHTML` to inject pre-built HTML strings. The strings are static template literals, not user input, so the XSS risk is low, but a future contributor who interpolates any non-static value (e.g. a query-param-driven scenario) will introduce an injection without TypeScript catching it.
- `packages/web/src/data/commands.ts` — duplicate-of-source-of-truth concern. Every command shape lives here (e.g. `commandGroups`) and is consumed by the docs site, but the same commands are also rendered in `packages/web/src/views/home/terminal-demo/TerminalScene.astro` and `packages/cli/cmd/*`. A new CLI command requires editing three files. The `test/docs.test.ts:23-27` test catches only `command` string drift, not flag drift.

## Branching / Release Concerns

The repository runs an unusual three-track release model (alpha / beta / main) wired up via three `release-please-config.*.json` files and one `release-please.yml` workflow that branches on `github.ref_name` (`.github/workflows/release-please.yml:14-48`). The implications:

- **Three concurrent release trains, three concurrent `VERSION` files.** `VERSION` is the single source of truth, but each branch is expected to carry a different value (`release-common.sh:42-69`). A force-push or out-of-order merge between branches will conflict on `VERSION`, `release-please-manifest.json`, and `packages/cli/packages/npm/package.json`. The `auto-merge-release-please.yml:28-65` validation reduces but does not eliminate this risk; the workflow does not check `VERSION` content, only PR provenance and title.
- **Auto-merge guard depends on PR title format.** `auto-merge-release-please.yml:59-62` blocks auto-merge if the title contains `-(alpha|beta).` AND the base branch is `main`. This is a positive match against the prerelease suffix, but if a release-please version is published with a non-prerelease-looking prerelease tag (e.g. `1.0.0-rc1`), the regex misses it. Future authors adding new prerelease tracks must update this guard or accept accidental `main` merges.
- **Two reverts in the last 30 commits** (`bdf6318 Revert "Merge pull request #18 …"`, `a3f4133 Revert "Merge pull request #17 …"`) — both auto-merge release-please PRs that reached `main` incorrectly. The current guard is the post-mortem mitigation. Expect the reverts to recur if release-please changes its PR title format upstream.
- **Alpha branch is effectively abandoned at HEAD.** `git log origin/alpha` returns a single commit `a72955f feat: add alpha-ready skill-organizer cli`. After that, all work has landed on `beta` and then `main`. The `alpha` config (`release-please-config.alpha.json`) is still live, and a push to `alpha` will trigger the alpha release-please job (`release-please.yml:15-25`). If `alpha` is not a release track anymore, delete the branch and the config file; otherwise the config drift between the `alpha`-tagged `VERSION` and the `main`-tagged `VERSION` will be permanent.
- **Stable releases require `HOMEBREW_TAP_GITHUB_TOKEN`** (`docs/releasing.md:149-152`, `release-stable.sh:13`, `release.yml:36`). The token must be added to the repository as a secret. The pre-flight warning at `scripts/release-common.sh:88-93` is the only reminder; an operator who runs the stable release script locally without the secret will only see a warning, not an error.
- **Release scripts reference a token that no longer exists.** `scripts/release-alpha.sh:12`, `scripts/release-beta.sh:12`, and `scripts/release-stable.sh:12` all call `release_warn_missing_secret NPM_TOKEN`. npm trusted publishing (`docs/releasing.md:194`, `publish-npm.yml:9`) means `NPM_TOKEN` is not used anywhere. The pre-flight warning is now a noise signal. Either drop the `NPM_TOKEN` line or document the legacy check.
- **Three config files, one schema.** `release-please-config.alpha.json`, `release-please-config.beta.json`, and `release-please-config.stable.json` differ only in `prerelease` and `prerelease-type`. A change to the stable config (e.g. adding a new `extra-files` entry) must be replicated in the alpha and beta configs by hand. There is no template.
- **`packages/cli/packages/npm/package.json` is hand-edited on release.** It is in the `extra-files` block of every config, but the field is read by `scripts/release-common.sh:13-15` to assert consistency. If release-please fails to write it (e.g. the new workflow version expects a different field name), the CLI will ship a stale version string in the npm package. No test guards this.
- **GoReleaser ignores windows/arm and windows/arm64** (`packages/cli/.goreleaser.yaml:24-30`). Linux and macOS arm64 users are covered, but Windows ARM users (Surface Pro X, etc.) are not. If you support Windows ARM, the goreleaser config must drop those `ignore:` entries; the build will start producing more artifacts.
